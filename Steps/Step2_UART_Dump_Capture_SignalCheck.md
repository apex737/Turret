## 3. UART 설정과 연결

### CubeMX 설정
| 항목 | 값 | 이유 |
|---|---|---|
| USART2 Baud | **921600** | 12KB 패킷 ≈ 0.13초 (115200이면 ≈1.07초 → 홀드오프 **(SW 디바운싱)** 1초보다 길어 다음 트리거가 송신 중이라 버려짐) |
| DMA | USART2_TX, DMA1 Stream6 Ch4, **Normal**, Byte, MemInc | `HAL_UART_Transmit_DMA` 사용 |
| NVIC | **USART2 global interrupt ON** | F4 HAL은 DMA 완료 후 UART TC 인터럽트에서 `HAL_UART_TxCpltCallback` 호출 → 꺼져 있으면 `dump_busy()`가 영원히 true |
| 포트 | ST-LINK 가상 COM = **COM8** | CubeMonitor(디버그 포트)와 동시 사용 가능 |

### 앱 연결 (`Core/app/src/app.c`)
- UART 하드웨어 초기화는 CubeMX(`MX_USART2_UART_Init`, `HAL_UART_MspInit`)가 이미 함.
- 앱에서 할 일:
  - `app_init`: `dump_init(app->huart)` → `capture_init(NULL)` → ADC 시작 → TIM2 시작(항상 마지막)
  - 메인 루프: `adc_get_frame()` 직후 **`capture_on_frame(&frame, seq)`** 호출
  - `HAL_UART_TxCpltCallback` → `dump_on_tx_cplt(huart)`
  - `HAL_GPIO_EXTI_Callback` (B1) → `capture_request_manual()`

## 4. 왜 덤프/캡처인가 — "차량 블랙박스" 방식

- 연속 전송 불가: 50k샘플 × 3ch × 2B = **300 KB/s** > UART 921600bps ≈ **92 KB/s**
- 그래서 **소리가 났을 때 그 전후만** 보낸다.

| 블랙박스 | 이 프로젝트 |
|---|---|
| 충격 감지 센서 | **capture.c** — "소리 났다" 판단 (언제 보낼지) |
| 충격 직전 영상도 저장 | 직전 프레임 + 트리거 프레임 (40.96ms) |
| 영상 파일로 포장 | **dump.c** — 패킷 포장 + CRC + UART DMA 송신 (어떻게 보낼지) |
| PC에서 재생 | **dump_viewer.py** — 수신·검증·저장(npz)·그래프 |

### 4.1 UART가 느린데도 "실시간"으로 보이는 이유

연속 스트리밍이 아니라 **찍어 두고 나중에 보내는** 방식이기 때문.

| 항목 | 값 |
|---|---|
| 한 패킷에 담긴 소리 | 40.96ms (2프레임) |
| 패킷 크기 / 전송 시간 | 12,310B / ≈134ms (921600bps, 바이트당 10비트) |
| 최대 전송 빈도 | holdoff 때문에 1초에 1패킷 → 평균 ≈12KB/s (링크 용량 92KB/s의 ≈13%) |

- **샘플링은 UART와 무관**: ADC+DMA가 50kHz로 RAM에 먼저 받아 두고, UART는 이미 저장된 것을 천천히 내보냄.
- **시간축은 도착 시각이 아니라 샘플 번호**로 만듦 (`t = i / fs`) → 전송이 느려도 20µs 해상도는 그대로.
- 여기서 "실시간"은 연속 재생이 아니라, 소리가 난 뒤 전송 시간(≈134ms) + PC가 그리는 시간이 지나면 그림이 갱신된다는 뜻.

### 4.2 AWD(Analog Watchdog) 트리거와 비교

- AWD = ADC 하드웨어가 샘플마다 `low < 값 < high` 창을 벗어났는지 검사해 인터럽트를 올리는 기능.
- 처음엔 이걸로 트리거할 생각이었음.

| | AWD | 현재 (프레임 RMS) |
|---|---|---|
| 판정 단위 | 샘플 1개 (20µs) | 프레임 (20.48ms) |
| CPU 부담 | 0 | 프레임당 ≈3k 샘플 연산 (F446에서는 무시할 수준) |
| 임계값 | 고정 (바이어스 ± X) | 잡음 바닥에 적응 |
| 스파이크/EMI 한 점 | 바로 트리거 | 에너지 평균이라 견딤 |
| 큰 소리가 계속될 때 | 인터럽트가 반복 → 끄고 다시 켜는 처리 필요 | holdoff로 처리 |

- **결론: 지금 용도(덤프/디버그)에는 프레임 RMS가 더 합리적.**
  - TDOA는 어차피 프레임 전체를 보고 계산 → 트리거의 샘플 단위 지연은 이점이 아님. 정밀도는 트리거 타이밍이 아니라 샘플 데이터에서 나옴.
  - 게인을 바꿔 가며 실험하는 단계라 고정 임계값은 매번 다시 맞춰야 함.
- AWD가 맞는 경우: CPU를 재우고 소리가 날 때만 깨우는 저전력 대기. 나중에 최적화로 고려.

## 5. capture — 트리거 방식

매 프레임(20.48ms) `capture_on_frame()`:
```
① 채널별 AC RMS 계산 → level = 3채널 중 최대
② threshold = max(k_on × 잡음바닥, min_rms)
③ level > threshold && 학습 끝 && 홀드오프 끝 → 송신 [직전 프레임 | 현재 프레임]
④ 조용한 프레임(또는 학습 구간)이면 잡음바닥 EMA 갱신
⑤ 현재 프레임을 '직전 프레임'으로 보관
```

| 파라미터 | 기본값 | 이유 |
|---|---|---|
| `learn_frames` | 25 (≈0.5초) | 부팅 직후 방 잡음 학습, 트리거 안 함 → **리셋 직후 0.5초는 조용히** |
| `k_on` | 4.0 (≈+12dB) | 잡음이 우연히 튀는 정도로는 트리거 안 되게 |
| `min_rms` | 20 LSB | 잡음바닥이 아주 낮을 때 오트리거 방지 |
| `holdoff_frames` | 50 (≈1초) | 잔향 재트리거 방지 + 송신 시간 확보 |
| `floor_alpha` | 0.05 | 잡음바닥 추종 속도. 조용한 프레임에서만 갱신 (박수로 임계값이 오르지 않게) |

- **직전 프레임을 같이 보내는 이유**: 트리거는 소리가 커진 뒤에 걸림 → 직전 20ms를 붙여야 **소리 시작점**이 항상 포함됨.
- 직전 프레임은 `frame_seq == 이전 + 1`일 때만 이어붙임 (중간 drop 시 시간축 끊김 방지).

### 자동 트리거 vs B1 버튼
| | 자동 | B1 버튼 (수동) |
|---|---|---|
| 조건 | 임계값 초과 + 학습/홀드오프 끝 | **무조건** (학습·홀드오프 무시) |
| 제목 표시 | `[PRETRIG]` | `[MANUAL PRETRIG]` |
| 용도 | 소리 캡처 | 조용한 상태 **잡음 기준** 캡처, **송신 경로만** 시험 |

둘 다 이전 송신이 진행 중이면 그 프레임에서는 보내지 못함. 수동 요청은 플래그가 남아 다음 프레임에 재시도, 자동 트리거는 조건이 계속 맞을 때만 다시 시도.

### 5.1 작동 흐름

프레임이 하나 찰 때마다 `capture_on_frame()`이 한 번 실행됨.

```
ADC+DMA ─(1024샘플 참)─▶ adc_get_frame() ─▶ capture_on_frame(frame, seq)

 1) 측정   frame_stats → rms[3], clip[3]
           level = max(rms),  clip_sum = 합
           frames++,  holdoff > 0 이면 holdoff--
 2) 판정   thr  = max(k_on × floor, min_rms)
           trig = (level > thr)
 3) 송신   manual  또는  (학습 끝 AND holdoff == 0 AND trig) 이면
             dump_busy() ? ── 예 ──▶ 이번 건 포기
                          └─ 아니오 ─▶ prev가 바로 앞 번호인가?
                                        ├ 예     → [prev | 현재] 2프레임 + PRETRIG
                                        └ 아니오 → 현재 1프레임만
                                      성공하면 holdoff = 50, manual = false
 4) 학습   learning 또는 !trig 일 때만  floor += α × (level − floor)
 5) 보관   prev = 현재 프레임, prev_seq = seq
```

시간축으로 보면:

```
프레임   … │ N-2 │ N-1 │  N  │ N+1 … N+50 │ N+51
level       조용   조용   큼     잔향          조용
                          ↑ N이 끝난 뒤에 판정 → [N-1 | N] 송신
                                └── holdoff 50프레임(≈1초) ──┘ 다시 트리거 가능
```

- 트리거는 하드웨어 기능이 아니라 **프레임마다 돌리는 소프트웨어 판정**. 판정이 프레임이 끝난 뒤에 나오므로 직전 프레임을 항상 보관해 둠.
- `prev` 갱신(5)이 맨 끝인 이유: 그래야 3)에서 볼 때 `prev`가 정말 "직전" 프레임.

### 5.2 용어 — AC RMS, LSB

- **AC RMS = 표준편차**. RMS는 `sqrt(mean(x²))`, 표준편차는 평균을 뺀 값으로 같은 계산을 한 것. 마이크 신호는 바이어스(≈2048) 위에서 흔들리므로 평균(DC)을 뺀 RMS가 곧 표준편차.
  - 통계에서는 "표준편차(흔들림의 산포)", 신호처리에서는 "AC RMS(신호의 크기)". 소리가 크다 = 진동 폭이 크다 → 같은 말.
- **LSB = ADC 숫자 1칸**. 12비트 ADC의 0~4095에서 1이 1 LSB. 3.3V 기준 ≈0.8mV → 20 LSB ≈ 16mV.
  - 코드에는 전압 변환이 없고 ADC 정수만 있으므로 LSB가 가장 자연스러운 단위.
- dB는 배수의 다른 표현 (+12dB ≈ 4배, +6dB ≈ 2배).

### 5.3 `frame_stats()` — 한 번의 루프로 RMS와 클리핑 계산

| 출력 | 의미 | 용도 |
|---|---|---|
| `rms[ch]` | 평균을 뺀 신호의 크기 [LSB] | 트리거 판정 |
| `clip[ch]` | 8 이하 또는 4087 이상인 샘플 수 | flags의 CLIP 비트 |

```
num = N·Σv² − (Σv)²        rms = sqrt(num) / N
```

- 유도: 분산 = Σv²/N − (Σv/N)², 양변에 N²을 곱하면 위 식. 평균을 먼저 구해 빼는 두 번째 루프가 필요 없음.
- 자료형: `Σv`는 최대 ≈420만 → 32비트. `Σv²`는 최대 ≈172억 → **64비트 필요**. `(uint64_t)s * s`의 캐스트가 없으면 32비트에서 오버플로.
- 클리핑 경계를 0/4095가 아니라 8/4087로 둔 이유: 끝에 아슬아슬하게 붙은 샘플도 세기 위해.

### 5.4 상태 관리

실행 중 바뀌는 값은 `capture_state_t` 구조체 하나(`stat`)로, 설정은 `capture_cfg_t`(`conf`)로 분리.

| 상태 | 켜는 곳 | 끄는 곳 | 성격 |
|---|---|---|---|
| `s_busy` (dump) | 송신 시작 직전 (main) | 송신 완료 인터럽트 | 버퍼 잠금 |
| `stat.manual` | 버튼 인터럽트 | 송신 성공 시 (main) | 요청 기억 |
| `stat.holdoff` | 송신 성공 시 50 | 프레임마다 −1 | 카운트다운 |
| `stat.prev`, `prev_seq`, `prev_valid` | 프레임마다 맨 끝에서 갱신 | — | 한 프레임 이력 |
| `clip`, `flags` | 프레임마다 새로 계산 | — | 상태가 아니라 그때그때의 결과 |

- 인터럽트와 main이 같이 쓰는 값(`s_busy`, `manual`)만 `volatile`.
- `manual`은 **송신에 성공했을 때만** 지움 → 송신 중이라 실패하면 다음 프레임에 자동 재시도.
- flags는 비트 자리가 서로 달라(0x01, 0x02, 0x04) OR 연산으로 합침.

### 5.5 EMA 잡음 바닥 · 적응형 트리거 · holdoff

- **EMA**: `floor += α × (level − floor)` — 새 값 쪽으로 α만큼만 다가가는 평균. 과거 값을 배열로 저장하지 않고 float 하나로 유지.
  - α = 0.05 → 20프레임(0.41초) 뒤 변화의 64%, 60프레임(1.2초) 뒤 95%를 따라감.
- **적응형 트리거**: 문턱을 고정값이 아니라 `k_on × floor`로 둠 → 방이 시끄러워지면 문턱도 같이 올라감.
  - 트리거된 프레임은 floor 갱신에서 제외 → 소리 자체가 문턱을 끌어올리지 못하게.
  - `floor`는 1 미만으로 내려가지 않게 막음 (문턱이 0이 되는 것 방지).
- **holdoff (소프트웨어 디바운싱)**: 버튼 디바운싱과 같은 발상. 한 번 반응한 뒤 일정 시간 무시하되, `delay`로 멈추지 않고 프레임마다 카운터를 줄여 main 루프가 계속 돎.
  - `if (stat.holdoff) stat.holdoff--;`의 `if`: `uint16_t`라 0에서 빼면 65535가 되어 영원히 금지 상태가 됨.

### 5.6 파라미터 조정 방향

| 파라미터 | 값 | 올리면 | 내리면 |
|---|---|---|---|
| `k_on` | 4.0 | 오트리거 감소, 약한 소리 놓침 | 민감해짐, 잡음에 걸림 |
| `min_rms` | 20 LSB | 조용한 방에서 작은 소리 놓침 | 전원 잡음 같은 것에 걸림 |
| `learn_frames` | 25 (0.5초) | 부팅 후 대기가 길어짐 | 학습이 덜 된 floor로 시작 |
| `holdoff_frames` | 50 (1초) | 연속된 소리를 덜 자주 캡처 | 잔향에 재트리거. 송신 시간(≈7프레임)보다는 커야 함 |
| `floor_alpha` | 0.05 | 환경 변화를 빨리 따라가지만 느린 소리에 둔감 | 안정적이지만 환경 변화에 늦음 |

값은 이론이 아니라 실험으로 정함 (스냅이 안 잡히면 `k_on`을 낮추는 식).

### 5.7 한계와 개선 후보

**① 서서히 커지는 소리를 못 잡음** — 입으로 점점 커지는 소리(다가오는 비행체 흉내)를 냈을 때 트리거되지 않음.

- 원인: 서서히 커지면 매 프레임 `level`이 `4 × floor`를 넘지 못함 → "조용한 프레임"으로 분류되어 floor를 올리는 데 쓰임 → **문턱이 소리를 따라 도망감**.
- 조건: 프레임당 `(k_on − 1) × α` = 15% 넘게 계속 커져야 트리거 = **≈59 dB/s 이상**.
- 소리가 일정해진 뒤에는 floor가 그 크기에 수렴 → 그 소리는 "평소 잡음" 취급.

트리거 로직을 Python으로 옮긴 시뮬레이션 결과 (보드 측정 아님. 잡음 4 LSB → 400 LSB, 40dB 상승 가정):

| 커지는 데 걸린 시간 | 상승 속도 | 트리거 | level ÷ 문턱 (최대) |
|---|---|---|---|
| 0.1초 | 400 dB/s | 됨 | 20.0 |
| 0.5초 | 80 dB/s | 됨 | 12.3 |
| 0.7초 | 57 dB/s | 안 됨 | 0.97 |
| 2초 | 20 dB/s | 안 됨 | 0.49 |
| 5초 | 8 dB/s | 안 됨 | 0.35 |


- **보드에서 확인됨**: 디버거 Live Expressions에서 `stat.floor`가 소리를 따라 올라감을 확인함.
- 개선 후보: **비대칭 EMA** (올라갈 때 α = 0.001, 내려갈 때 0.05). 같은 시뮬레이션에서 2초 상승은 0.68초, 5초 상승은 1.74초 시점에 트리거.
  - 대가: 환경 잡음이 실제로 커지면(선풍기 등) 적응하는 수십 초 동안 1초마다 계속 트리거.


- 즉 지금 구조는 **"갑자기 커지는 소리(onset)" 검출기**. 계속 나는 소리가 대상이면 검출 방식과 GCC-PHAT 분석 구간 설계가 모두 달라짐 → 대상 소리부터 결정.

**② 짧은 소리에 둔감** — 20ms 전체 RMS라서 ≈1ms짜리 스냅은 평균에 묻혀 약 −13dB로 측정됨 (`k_on` = +12dB와 비슷한 크기).

- 개선 후보: 프레임을 64~128샘플 서브블록으로 나눠 블록별 RMS의 최댓값을 level로 사용, 또는 평균을 뺀 최대 절대 편차(peak) 사용.

### 5.8 CubeMonitor 관찰 코드 제거 (2026-10-10)

- 제거: `capture_status_t` / `g_capture` (rms, clip, floor, threshold, trig_cnt, skip_busy), `app.c`의 `mon_mean`, `mon_p2p`, `mon_rms`, `mon_drop_cnt`, `mic_stats()`.
- 유지: `mon_frame_cnt`는 프레임 번호로 쓰이고 있어 `frame_cnt`(static)로 이름만 바꿈.
- 이유: 쓰기만 하고 읽는 곳이 없는 관찰용 사본이라 동작에는 영향 없음.
- 잃은 것: **트리거가 안 될 때** rms와 문턱을 볼 창. 덤프는 트리거된 뒤에만 오므로, 안 잡히는 원인은 디버거로 `stat`을 직접 봐야 함. 송신 중이라 버린 횟수도 더는 세지 않음.

## 6. dump — 패킷 형식

```
[FF FF FF FF][헤더 16B][payload ch0[n] | ch1[n] | ch2[n]][CRC16 2B]
```
| 필드 | 의미 |
|---|---|
| sync `FF FF FF FF` | 패킷 시작. ADC 값 ≤ 0x0FFF라 payload에서 FF 4연속 불가 → 오인 없음 |
| ver=2, type=0x01, ch=3 | 형식 버전, RAW_ADC, 채널 수 |
| flags | `0x01` CLIP, `0x02` MANUAL, `0x04` PRETRIG |
| seq | 송신 패킷 번호 (누락 검출) — ⚠️ **MCU 리셋 시 0부터 다시 시작** |
| frame_seq | ADC 프레임 번호 (시간 정보, 나중에 MCU 결과 패킷과 짝짓기용) |
| n, len | 채널당 샘플 수(1024×프레임 수), payload 바이트 수 |
| CRC-16/CCITT-FALSE | ver~payload 끝. Python `binascii.crc_hqx(data, 0xFFFF)`와 동일. 12KB 기준 ≈2ms |

- **DMA 송신 이유**: CPU 직접 송신이면 0.13초 동안 ADC 프레임 6개를 놓침.
- 송신 버퍼는 정적 12,310B (DMA가 읽는 동안 스택 사용 불가).

### 6.1 작동 흐름

dump는 "언제" 보낼지는 모르고, capture가 시키면 포장해서 보내기만 함.

```
main 루프                              DMA + UART              인터럽트
dump_send_frames()
 ├ busy 이면 false 반환
 ├ 헤더 채움 (seq++)
 ├ memcpy로 tx_buf에 복사
 ├ CRC 계산
 ├ busy = true
 └ HAL_UART_Transmit_DMA() ──────▶ tx_buf를 한 바이트씩 전송
   즉시 return true                  (12,310B ≈ 134ms)
 … main은 계속 프레임 처리 …               └────────▶ TxCplt → dump_on_tx_cplt(): busy = false
```

| 함수 | 한 줄 설명 |
|---|---|
| `dump_init` | UART 핸들 저장, 상태 초기화 |
| `dump_busy` | 송신 중인지 확인 (송신 버퍼가 하나뿐) |
| `dump_send_frames` | 프레임 N개를 포장해서 송신 시작 (핵심) |
| `dump_send` | 프레임 1개용 단축 함수 (`static inline`) |
| `dump_on_tx_cplt` | 송신 완료 알림을 받아 busy 해제 |

### 6.2 패킷 바이트 배치

위의 "헤더 16B"는 sync를 뺀 값. 코드의 `dump_hdr_t`는 **sync 4B + 헤더 16B = 20B**.

| offset | 크기 | 필드 | 값 |
|---|---|---|---|
| 0 | 4 | sync | `FF FF FF FF` |
| 4 | 1 | ver | 2 |
| 5 | 1 | type | 0x01 |
| 6 | 1 | ch | 3 |
| 7 | 1 | flags | CLIP 0x01, MANUAL 0x02, PRETRIG 0x04 |
| 8 | 4 | seq | 패킷 번호 |
| 12 | 4 | frame_seq | 마지막 프레임 번호 |
| 16 | 2 | n | 채널당 샘플 수 (2프레임이면 2048) |
| 18 | 2 | len | payload 바이트 수 (2프레임이면 12,288) |
| 20 | len | payload | 아래 그림 |
| 20+len | 2 | crc16 | ver부터 payload 끝까지 (sync 제외) |

```
payload:  │ ch0 prev │ ch0 현재 │ ch1 prev │ ch1 현재 │ ch2 prev │ ch2 현재 │
            1024샘플씩, 샘플 하나는 uint16 little endian
```

- 채널이 바깥 루프인 이유: PC가 채널 하나의 파형을 연속된 덩어리로 바로 읽을 수 있게.
- `__attribute__((packed))`: 컴파일러가 필드 사이에 빈칸을 넣지 못하게 해서 구조체 배치 = 전송 바이트 배치.
- `_Static_assert(sizeof(dump_hdr_t) == 20)`: 필드를 고치다 PC와 형식이 어긋나면 컴파일 단계에서 막음.

### 6.3 `dump_frame_t` — typedef로 배열을 한 덩어리로 다루기

`typedef uint16_t dump_frame_t[3][1024];` = 2차원 배열 전체에 "프레임"이라는 타입 이름을 붙인 것 (구조체가 아니라 배열 타입).

| 코드 | 의미 |
|---|---|
| `const dump_frame_t *f` | 프레임 하나(6144B) 전체를 가리키는 포인터. 복사 없이 전달 |
| `(*f)[ch]` | 그 프레임의 채널 `ch` (1024샘플 배열) |
| `sizeof(stat.prev)` | 6144. 크기 정보가 타입에 들어 있어 `memcpy`에 그대로 씀 |
| `const dump_frame_t *const fr[2] = {&stat.prev, frame}` | 프레임 포인터 2개짜리 배열. 두 프레임을 이어 붙이지 않고 넘김 |

- `app.c`의 `(const dump_frame_t *)&frame` 캐스트: `frame`이 같은 크기의 배열이라 가능. `const`를 붙이기 위한 것.

### 6.4 구현 포인트

- **busy를 DMA 시작 전에 켬**: 순서가 반대면, 완료 인터럽트가 먼저 와서 `false`로 만든 뒤 `true`로 덮어써 busy가 영원히 켜질 수 있음.
- **복사 후 송신**: `memcpy`로 `tx_buf`에 옮긴 뒤 DMA를 시작 → 함수가 돌아오면 원본 프레임을 바로 덮어써도 됨.
- **`tx_buf`가 `static`인 이유**: DMA는 함수가 끝난 뒤에도 이 메모리를 계속 읽음. 지역변수(스택)는 함수가 끝나면 사라짐.
- **`seq`는 DMA 시작이 실패해도 이미 1 증가**: 실패 시 PC에서 `seq_gap`으로 한 번 보일 수 있음.
- **CRC**: 데이터를 16비트 "지문"으로 요약. 송·수신측이 각자 계산해 값이 다르면 전송 중 깨진 것. 알고리즘 자체보다 "양쪽이 같은 공식"이라는 점이 중요.

## 7. dump_viewer.py — 결과 읽는 법

### 콘솔
```
seq 3  saved dumps/f_000003.npz  (1.52 s since last)  {'ok': 4, 'crc_fail': 0, 'bad_hdr': 0, 'seq_gap': 0}
```
| 항목 | 0이 아니면 |
|---|---|
| `crc_fail` | 보레이트 불일치, `printf` 혼입, 잡음 |
| `bad_hdr` | 거의 0이어야 정상 |
| `seq_gap` | PC가 패킷을 놓침 (리셋 직후 1회는 정상) |

### 그래프 3단
| 그래프 | 내용 | 볼 것 |
|---|---|---|
| **위: 전체 40.96ms** | -20 ~ 0ms = 직전 프레임,  0 ~ 20ms = 트리거 프레임 (빨간 점선 = 트리거 프레임 시작) | 소리 전 구간이 조용한가, 0·4095 점선에 붙었나(클리핑) |
| **가운데: 시작점 확대** | onset 기준 −0.5~+1.5ms, 평균 제거, **점 하나 = 20µs** | **같은 마루·골을 짝지어 채널 간 몇 점 밀렸나 = TDOA**. Δn × 20µs, Δn × **6.86mm** |
| **아래: 스펙트럼** | Hann 창, dBFS (0dBFS = 진폭 2048 사인), 로그 주파수, 초록 띠 = BPF 후보 (`--bpf`로 변경) | 에너지 대역, 험/스위칭 노이즈 선 → BPF 대역 결정 |

- onset(빨간 점선) = 최대 진폭의 20%(또는 잡음×6)를 처음 넘은 지점 → **대략값**. 실제 시작은 선들이 기준선에서 갈라지는 지점.
- 타당성: |Δn| ≤ 마이크 간격 / 6.86mm (예: 10cm → ≈15샘플)

### 7.1 수신 처리 순서

UART는 패킷 경계가 없는 바이트 스트림이라 PC가 직접 패킷을 잘라냄.

1. 시리얼에서 들어온 바이트를 버퍼에 쌓음
2. `FF FF FF FF`를 찾아 패킷 시작을 잡음
3. 헤더를 검증하고 `len`만큼 다 도착할 때까지 기다림
4. CRC가 맞으면 `(ch, n)` 배열로 바꿔 npz로 저장 (틀리면 1바이트만 버리고 다시 sync 탐색)
5. matplotlib 대화형 모드(`plt.ion()`)로 같은 창을 지우고 다시 그림

### 7.2 캡처 해석 예시 (seq 22)

| 항목 | 관찰 | 판단 |
|---|---|---|
| 클리핑 | 전 채널 0, 소리 전 구간은 완전히 조용 | 좋음. 트리거와 직전 프레임 설계가 잘 동작 |
| 진폭 | p2p 430 / 985 / 511 (범위 4096 중 10~24%) | 게인에 여유가 큼 |
| 채널 차이 | rms 29 / 63 / 31. MIC2가 약 2배(+6dB) | 아래 ① |
| 스펙트럼 | 에너지 대부분이 2~6kHz (−45~−55dBFS). 초록 띠(150~2000Hz)는 −60~−70dBFS | **BPF가 가장 센 구간을 잘라내고 있음** |
| 노치 | 700Hz 부근에 3채널 공통 노치 | 반사음 간섭. 채널 결함 아님 |
| 파형 | 채널마다 모양이 달라 마루·골 짝짓기가 어려움 | 눈으로 읽은 지연은 ±수 샘플 오차 → GCC-PHAT 필요 |

튜닝 방향:

- **① 게인**: GCC-PHAT는 주파수별 크기를 1로 정규화 → **진폭 차이는 지연 추정에 거의 영향 없음**. 중요한 것은 클리핑 없음, 충분한 SNR, 채널 간 위상 응답. 올린다면 전체를 2~3배 올려 가장 큰 채널의 p2p가 ≈2500~3000이 되게.
- **② BPF 대역**: 150 ~ 2000 / 1000 ~ 4000 / 2000 ~ 5000Hz를 비교해 상관 피크가 가장 뾰족하고 안정적인 대역을 선택. 5kHz 이상은 채널 간 응답 차이가 있어 올리지 않는 쪽이 안전.
- **③ 분석 구간**: onset선은 20% 임계라 실제 시작보다 늦음 → 창은 onset보다 0.5~1ms 앞에서 시작. 잔향이 길어 창이 길수록 반사음이 섞임 → 2 / 3 / 5 / 10ms 비교.

## 8. 왜 GCC-PHAT을 Python에서 먼저 만드나

MCU에서 바로 구현하면 결과가 이상할 때 원인 후보(알고리즘 이해 / 파라미터 / CMSIS-DSP 사용법 / 버퍼·인덱스 버그 / 매번 다른 소리)를 **구분할 수 없음**.

| 이점 | 내용 |
|---|---|
| 재현성 | 같은 npz로 무한 반복. 파라미터 바꿔 몇 초 만에 비교 |
| 가시성 | 상관 곡선 전체, 피크 선명도, 반사음 2차 피크까지 보임 |
| 설계 결정 | BPF 대역, 분석 구간 길이, FFT 크기·제로패딩, 2차 보간 효과를 데이터로 결정 |
| 정답지(golden model) | MCU 결과를 `frame_seq`와 함께 보내 같은 프레임의 Python 결과와 비교 → 차이 ≤ 0.1샘플이면 구현 OK. 틀리면 MCU 코드만 의심 |

```
Python : 알고리즘 설계 + 파라미터 결정 + 정답지   (빠른 반복, 다 보임)
   ↓ 확정된 설계 이식
MCU    : CMSIS-DSP 구현 → 같은 프레임 결과를 Python과 비교   (구현 버그만 찾으면 됨)
```
