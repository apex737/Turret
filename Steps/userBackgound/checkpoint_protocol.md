# 이해 점검 규칙 — Claude가 개발 중간에 끼어드는 방식

> 작성: 2026-10-22 · 읽는 이: **Claude** (작업 시작 전에 이 파일을 읽고 그대로 따른다)
> 함께 쓰는 파일: [background.md](background.md) (개념 지도·판정), [background_quiz.md](background_quiz.md) (문항·답·채점 원본)

## 0. 왜 이 규칙이 있나

- 빠른 구현은 유지한다. 그런데 Claude가 계산·시뮬레이션·데이터 분석으로 결론을 내고 사용자는 결과만 받는 일이 쌓이면, 프로젝트가 **사용자에게 블랙박스**가 된다.
- 목표: **문서와 AI 없이 사용자 혼자 이 프로젝트를 복원할 수 있다.** 구체적으로는 다음 세 가지다.
  1. 데이터 흐름을 블록 단위로 설명한다 (마이크 → ADC → … → 결과).
  2. 튜닝 파라미터마다 역할, 키우거나 줄이면 생기는 일, 지금 값의 근거를 말한다.
  3. 주요 결정마다 [decisions.md](../decisions.md)의 "설명할 수 있다" 네 가지(버린 선택지, 근거 숫자, 대가, 다시 결정할 조건)에 답한다.
- 이 규칙은 **일부러 불편하게 만드는 장치**다. 사용자가 모르는 채로 다음으로 넘어가는 것을 막는 것이 목적이다. 문항은 짧게 내지만, 건너뛰게 두지는 않는다.

## 1. 언제 끼어드나 (트리거)

| 트리거             | 상황                                                                                 | 문항 수 | 어디서 묻나                              |
| ------------------ | ------------------------------------------------------------------------------------ | ------- | ---------------------------------------- |
| **T1 예측**        | Claude가 시뮬레이션·측정 분석을 **돌리기 직전**                                      | 1       | 대화                                     |
| **T2 결정 체크**   | Claude의 분석에서 Action A(설계 선택, 버림, 다음 실험)가 나왔을 때. **적용·커밋 전** | 1 ~ 3   | 대화                                     |
| **T3 파라미터**    | 튜닝 상수를 새로 정하거나 값을 바꿀 때 (`tdoa.h`, `preproc.h`, 학습 문턱 등)         | 1 ~ 2   | 대화                                     |
| **T4 단계 게이트** | Step의 통과를 판정하기 전, 그리고 다음 Step 코드를 쓰기 전                           | 5 ~ 8   | [background_quiz.md](background_quiz.md) |

**끼어들지 않는 경우**: 이름 짓기, 리팩터링, 버그 오타, 도구 사용법처럼 결정이 아닌 구현 세부. 판단 기준은 "이것이 decisions.md / decision.html에 들어갈 결정인가, 혹은 상수를 바꾸나"다.

**속도 예산**: T1 ~ T3은 합쳐서 한 작업 덩어리(대략 1 ~ 2시간)에 최대 3번, 각 5분 안에 답할 수 있는 크기로 낸다. 더 묻고 싶은 것은 T4로 미루고 [background_quiz.md](background_quiz.md)의 "대기 문항"에 적어 둔다.

## 2. 문항 만드는 법 — Action A를 거꾸로 분해한다

Claude가 Action A에 이른 과정을 사슬로 적고, 각 고리에서 하나씩 묻는다.

```
Action A  ←  근거 숫자  ←  그 숫자를 낸 계산·시뮬레이션·측정  ←  그 계산의 전제 개념 (ID)
```

**예시** (decisions.md 3-1, 대역 500 ~ 3000 Hz → 150 ~ 2000 Hz)

| 고리      | 내용                              | 물을 것                                                       |
| --------- | --------------------------------- | ------------------------------------------------------------- |
| Action    | 상한을 2000 Hz로 낮춘다           | "상한을 3000 Hz로 두면 날개 소리에서 무엇이 생기나?"          |
| 근거 숫자 | c/(2d) ≈ 2450 Hz                  | "2450은 어떤 두 값으로 계산했나? 간격이 14 cm면 얼마가 되나?" |
| 계산      | 위상차가 π를 넘으면 2π만큼 감긴다 | "감기면 왜 가짜 봉우리가 생기나?"                             |
| 전제 개념 | T1 공간 앨리어싱 ← F2 지연 ↔ 위상 | (이미 ❌이면 F2부터 묻는다)                                   |

**문항 유형** — 한 번에 같은 유형만 내지 않는다.

| 유형      | 형태                                                                                                      | 잴 수 있는 것              |
| --------- | --------------------------------------------------------------------------------------------------------- | -------------------------- |
| 예측      | "이걸 돌리면 결과가 어떻게 나올 것 같나? 이유는?" (T1에서 결과 공개 전)                                   | 직관이 맞는지              |
| 설명      | "왜 A인가?"                                                                                               | 핵심 이유                  |
| 반사실    | "이 값을 2배로 하면? 이 가정이 깨지면?"                                                                   | 외운 것과 이해한 것의 구분 |
| 복원      | "문서를 닫고, 이 값을 처음부터 어떻게 정할지 절차를 써라"                                                 | 혼자 복원할 수 있는지      |
| 고장 진단 | "이 증상이 보이면 어디부터 의심하나?"                                                                     | 운용·디버깅 능력           |
| 짝        | "이 상수를 바꾸면 반대쪽(MCU ↔ PC)에서 같이 바꿀 것은?" ([README](../../README.md) "같이 고쳐야 하는 짝") | 시스템 전체 그림           |

**문항 규칙**

- 프로젝트의 실제 숫자를 쓴다 (50 kHz, 1024샘플, 7 cm, CPU 48% …). 교과서 문제로 바꾸지 않는다.
- 문항 안에 답이나 힌트를 넣지 않는다. 객관식은 쓰지 않는다 (찍어서 맞힐 수 있다).
- 코드나 문서를 열지 않고 답할 수 있어야 한다. 필요한 숫자는 문항에 준다.
- **채점 기준(기대 답의 핵심 1 ~ 3줄)은 문항을 낼 때 정하고, 답을 본 뒤에 바꾸지 않는다.** 기록할 때 문항과 함께 남긴다.
- 매번 "모름도 답이다. 확신(상 / 중 / 하)도 적어 달라"는 말을 붙인다.

## 3. 채점

[background.md](background.md)의 기준을 그대로 쓴다.

| 표시        | 뜻                                                 |
| ----------- | -------------------------------------------------- |
| ✅ Pass     | 핵심 이유가 맞다. 계산이 틀려도 이유가 맞으면 Pass |
| △ 근접      | Fail이지만 절반 이상 맞았다                        |
| ❌ Fail     | 핵심 이유가 빠졌거나 틀렸다                        |
| ⚠ 확신 오류 | 확신 상 / 중으로 틀렸다. 가장 먼저 고친다          |

- 채점은 답을 받은 바로 그 자리에서 한다. "맞은 것 / 빠진 것"을 한 줄씩 쓴다.
- Pass를 후하게 주지 않는다. 용어만 맞고 이유가 없으면 △다.
- **Pass 확정은 두 번이다.** 처음 Pass가 나오면 "Pass(1)"로 적고, 나중에 다른 상황의 응용 문제로 한 번 더 맞히면 ✅로 확정한다. 같은 문항을 다시 맞힌 것은 확정이 아니다.

## 4. 기대에 못 미치면

1. **바로 짧게 설명한다.** 기본 원리부터, 프로젝트 숫자로 3 ~ 8줄. 저장소 안에 해당 절이 있으면 위치를 같이 준다 ([TDOA 배경지식](../helper/TDOA_튜닝_배경지식.md), Step 문서). 설명했다고 판정이 바뀌지는 않는다.
2. **기록한다.**
   - [background_quiz.md](background_quiz.md): 맨 아래 "Part 3 — 진행 중 점검"에 문항, 답(사용자가 쓴 그대로), 채점 기준, 판정을 남긴다. 형식은 6절.
   - [background.md](background.md) 3절 개념 표: 개념이 이미 있으면 판정과 근거 문항을 갱신하고, 없으면 새 ID를 만든다 (같은 묶음의 다음 번호, 예: T4. 새 분야면 새 글자). 선후 그림에도 추가한다.
   - [background.md](background.md) 2절 Step 표: 그 개념이 쓰이는 Step에 ID를 붙인다.
   - [background.md](background.md) 4절 보완 순서: ⚠는 0단계에, 다음 작업을 막는 개념은 트랙 A에, 나머지는 트랙 B의 선후 순서 자리에 넣는다.
3. **다시 묻는다.** 같은 문항이 아니라 응용 문항으로 묻는다. 시점은 다음 T4, 또는 그 개념이 다시 쓰이는 T2 / T3다.

## 5. 진행을 막는 조건

빠른 구현을 위해 **Fail은 진행을 막지 않는다.** 대신 아래는 막는다.

| 조건                                             | Claude의 행동                                                                                      |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| T2 / T3 문항에 아직 답하지 않았다                | 그 Action을 적용하거나 커밋하지 않는다. 다른 독립 작업은 계속해도 된다                             |
| 사용자가 "나중에"라고 했다                       | 문항을 quiz 파일의 **대기 문항**에 옮기고 진행한다. 대기 문항이 남아 있으면 T4를 통과시키지 않는다 |
| 다음 Step이 직접 기대는 개념에 ⚠가 남아 있다     | 다음 Step 코드를 쓰기 전에 ⚠ 정정(짧은 설명 + 재답)을 먼저 제안한다                                |
| T4 게이트에서 그 Step 의존 개념의 절반 이상이 ❌ | 다음 Step으로 가기 전에 보완을 제안한다                                                            |

- 사용자가 "부채로 넘긴다"고 명시하면 따른다. 이때는 quiz 파일 해당 문항에 `부채로 넘김 (날짜, 이유)`를 적고, background.md의 해당 Step 줄에도 표시한다.
- **Step 상태는 두 가지로 따로 보고한다.** 구현 통과(측정 기준 충족)와 설명 가능(의존 개념 ✅ 비율). 예: "Step8 — 구현: 미통과(근접) / 설명: 1 / 8". 둘을 하나로 합쳐 "완료"라고 하지 않는다.

### background_quiz.md — 진행 중 점검 문항

```markdown
### Q29 `[T1]` 대역 상한과 공간 앨리어싱 ← 번호는 기존 다음부터

- 날짜 · 트리거: 2026-10-22 · T2 (Step7, 대역 결정)
- 계기: (Claude가 낸 결론 한 줄, 예: "상한을 2000 Hz로 낮춘다")

(문항)

답: (사용자 답 그대로)
확신: 상 / 중 / 하

채점 기준: (문항을 낼 때 정한 핵심 1 ~ 3줄)
판정: ❌⚠ — 맞은 것: … / 빠진 것: …
재답: (나중에 이어 씀, 처음 답은 지우지 않는다)
```

### background_quiz.md — 대기 문항

```markdown
## 대기 문항

- [ ] Q31 `[C1]` (한 줄 요약) — 2026-10-22 T3에서 미룸. T4(Step8) 전까지
```

### Claude가 Action A를 제안할 때 붙이는 줄

결론을 보고할 때 마지막에 한 줄을 붙인다. decisions.md / decision.html에 결정을 적을 때도 같은 줄을 넣는다.

```
기대는 개념: T1 ✅ · F2 △ · E3 ❌   → 점검 문항: Q29, Q30
```

결정과 개념 ID가 연결되어 있어야 나중에 "이 결정을 다시 하려면 무엇을 알아야 하나"를 거꾸로 찾을 수 있다.

## 7. T4 단계 게이트의 구성

Step 통과를 판정하기 전, 또는 다음 Step 코드를 쓰기 전에 한다. 5 ~ 8문항, 20 ~ 30분 안.

1. **복원 문항 1개 (필수)**: "문서를 닫고 이 Step의 처리 흐름을 블록으로 그리고, 튜닝 파라미터 3개의 역할과 지금 값의 근거를 써라."
2. **결정 문항 1 ~ 2개**: 이 Step에서 나온 decisions.md 결정 하나를 골라 네 가지(버린 선택지, 근거 숫자, 대가, 다시 결정할 조건)를 묻는다.
3. **대기 문항 전부**와, **Pass(1) 상태 개념의 확정용 응용 문항**.
4. **⚠ / ❌ 개념 재확인**: 이 Step이 기대는 것 중 아직 해결되지 않은 것.
5. 채점한 뒤 background.md 2절의 그 Step "설명 가능도"를 갱신하고, 5절 기준으로 진행 여부를 말한다.

## 8. Claude의 태도

- 묻는 목적은 점수가 아니라 측정이다. 틀린 것은 틀렸다고 분명히 말하고, 이해를 하지 못할 경우 이후 개발에서 예상되는 애로사항에 대해 명시한다.
- 사용자가 답을 모를 때 Claude가 대신 답을 써 주고 Pass로 처리하지 않는다.
- 사용자가 대화 중에 설명을 정확히 해냈으면, 그것도 근거로 판정을 갱신한다 (문항을 따로 내지 않아도 된다).
- 같은 개념을 ✅ 확정 뒤에 다시 묻지 않는다. 예외는 그 개념의 다른 응용이 새 결정의 근거가 될 때다.
- 설명은 사용자의 현재 수준에 맞춘다. 예컨대, [background.md](background.md) 에서 사용자가 학부 DSP 기초와 ML 평가 기초 지식이 부족하다고 판단되면 대학원 용어로 시작하지 않는다.
