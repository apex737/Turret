# Remark — 개발 원칙

> 기준: AI를 썼냐가 아니라, **내가 커밋한 모든 줄을 AI 없이 설명하고 고칠 수 있냐.**

---

## 1. 작업 루프 (모듈 단위로 반복)

속도와 체화를 **영역별로 나눈다.** 전부 느리게 가는 게 아니다.

```
AI로 빠르게 동작 확인 → 핵심부만 손으로 재구현 → 측정해서 비교·기록 → 다음 모듈
```

| 단계 | 할 일 | 산출물 |
|---|---|---|
| 1차 (AI, 빠르게) | 설계 결정을 AI 구현으로 검증. AI 코드는 한 줄씩 읽고 "왜"를 주석으로 단다 | 확정된 파라미터, 레퍼런스 코드 |
| 2차 (손, 범위 한정) | 핵심 파이프라인만 레지스터/LL로 재구현. 클럭·GPIO·통신은 HAL 유지 | 손으로 짠 코어 모듈 |
| 비교 | AI 버전 vs 내 버전 측정 (ISR 실행 시간, 루프 지연, 메모리, 코드 크기) | ADR 문서 1개 |

**2차를 살리는 조건 3가지**
- [ ] 날짜를 박는다 — 1차 확정 후 2주 안에 2차 착수
- [ ] 범위를 좁힌다 — 전체 no-HAL이 아니라 파이프라인 코어만
- [ ] 측정으로 끝낸다 — "X µs → Y µs, 이유는 ~" 한 문장이 나와야 완료

---

## 2. 손으로 vs 맡겨도 됨

| 반드시 손으로 | AI에 맡겨도 됨 |
|---|---|
| ISR, 콜백, 공유변수 처리 (volatile, critical section) | CubeMX/HAL 초기화 보일러플레이트 |
| 링버퍼, 상태머신, 타이머 기반 스케줄링 | 로그 파싱·플롯용 파이썬 스크립트 |
| 제어/필터 루프 (PID, 이동평균, 고정소수점) | 문서 포맷팅, 테이블 정리 |
| 비트 연산, 레지스터 직접 조작 | 처음 보는 라이브러리 API 탐색 |
| 디버깅 첫 30분 | 내가 짠 코드의 리뷰어 역할 |

---

## 3. 작업 습관

1. **역할 역전** — AI는 작성자가 아니라 리뷰어. 내가 먼저 짜고 "문제점 찾아줘".
2. **디버깅 30분 룰** — AI 켜기 전 30분은 디버거·watch·스코프로 직접 본다. 그 뒤엔 "내 가설은 이건데 맞냐"로 묻는다.
3. **하루 20분 카타** — 빈 에디터, 레퍼런스 없이 하나씩:
   링버퍼 / 디바운스 / 비트필드 조작 / 고정소수점 곱셈 / memcpy 구현
4. **닫고 설명하기** — AI가 짠 파일을 닫고 함수별로 소리 내서 설명. 막히는 함수 = 다시 짤 함수.

---

## 4. 모듈을 "이해했다"의 기준

1 ~ 2단계는 "설명할 수 있다". 실무면접은 3 ~ 5단계에서 갈린다.

| 수준 | 답할 수 있어야 하는 질문 | ✓ |
|---|---|---|
| 1. 기능 | 입력, 출력, 무엇을 하는가 | [ ] |
| 2. 원리 | 어떤 원리로 동작하는가 | [ ] |
| 3. 설계 이유 | 왜 이 방식인가, 다른 선택지는 뭐였고 왜 버렸나 | [ ] |
| 4. 시간·자원 | 언제 실행되나(ISR/태스크), 얼마나 걸리나, 메모리, 누구와 데이터 공유 | [ ] |
| 5. 실패 | 어떤 조건에서 깨지나, 깨지면 어떤 증상인가 | [ ] |
| 6. 검증 | 무엇을 측정해서 확인하나 | [ ] |
| 7. 변경 | 요구사항이 바뀌면 어디를 고치나 | [ ] |

### 예시: ADC-DMA 모듈

- **1~2** TIM 트리거로 3채널 샘플링, DMA로 버퍼 이동
- **3** 왜 폴링이 아니라 DMA인가, 왜 더블버퍼인가
- **4** 샘플링 주기 대비 GCC-PHAT 처리 시간 마진은? 콜백에서 처리하나, 플래그만 세우나
- **5** 처리가 늦어 DMA가 반쪽 버퍼를 덮어쓰면 어떤 증상이 나오나
- **6** GPIO 토글을 스코프로 찍어 확인
- **7** 마이크를 4개로 늘리면 뭐가 바뀌나

### 최종 테스트
